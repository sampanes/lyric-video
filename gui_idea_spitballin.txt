A few strong GUI ideas you have not called out yet:

A **“safe crop preview”** panel for every target ratio. Same background shown as 16:9, 9:16, 1:1, and 4:5, with subtitle-safe zones overlaid. That will save you from making a beautiful image that fails once cropped.

A **section timeline editor** that is not a full NLE, but lets you see blocks like Intro / Verse / Chorus / Bridge, drag boundaries, assign stills/loops, and attach prompt notes to each block.

A **“generate 4 variants for this section”** button. Same workflow, same theme, maybe different seeds or mild prompt variants, then let you mark one as winner. Much better than single-shot gambling.

A **subtitle proof mode** that renders one frozen frame from each section with the real font, outline, size, and lyrics placement on top. That catches readability problems early.

A **project memory pane** with approved lyrics, approved prompts, approved sections, known-good workflows, and rejected experiments. Basically a compact audit trail.

A **“use this as baseline”** feature. Pick one good image or loop and tell the system to derive adjacent sections from it, rather than starting every section from zero.

A **job batching view** that groups by backend automatically: all Flux stills, then all Wan loops, then FFmpeg assembly. That will matter once you automate warm-model batching.

A **diff view** for prompts and settings. Very useful when `*-2` goes insane and `*-3` is okay. Show exactly what changed in prompt, seed, denoise, frames, fps, etc.

A **“human approval required” checklist** with explicit states:

* lyrics approved
* timings approved
* prompts approved
* subtitle style approved
* render approved

A **lightweight “what changed?” card** after every run:

* workflow
* seed
* size
* prompt delta
* result path
* quick thumbs up/down note

A **font stress test mode**. Show a few nasty lyric lines with commas, weird spelling, apostrophes, long lines, repeated words, all-caps emphasis, and line breaks, across all target aspect ratios.

A **fallback mode selector**:

* still only
* still + FFmpeg motion
* subtle AI loop
* premium hero-shot mode
  This helps prevent overusing video generation when stills would be better.

A **review queue** for “needs attention” items:

* low readability
* missing approval
* missing background
* failed run
* possible seam issue
* possible crop issue

A **bounce-loop toggle** in the UI for subtle motion clips. Very relevant to your current use case.

A few gotchas you are likely to hit:

The biggest one is **state explosion**. Once you have songs, sections, targets, prompts, variants, workflows, seeds, approvals, fonts, and outputs, things get messy fast. You will need a very clear project data model.

Another is **false certainty from LLM suggestions**. The GUI may make suggestions feel “blessed” even when they are just rough drafts. You need candidate vs approved states everywhere.

**Font availability** is annoying. “Show me FFmpeg fonts” sounds simple, but actual renderable fonts may differ by machine, by ffmpeg build, by fontconfig/directwrite behavior, and by path. You will want a verified-font list, not just a guessed one.

**Preview mismatch** is another trap. A font preview in the GUI may not exactly match final FFmpeg render unless you are careful about using the same renderer assumptions.

**Prompt drift** can quietly ruin consistency. If every section gets lightly rewritten by an LLM, your video may feel visually disconnected. You will want some shared visual anchors per song.

**Comfy workflow brittleness** is real. Small UI-export differences, node renumbering, or model-name mismatches can break automation if your scripts depend on fragile node IDs.

**Terminal puppeting fragility** will bite you eventually. CLIs change, redraw, ask for confirmation, hang, or output weird junk. Treat CLI-driven LLM help as advisory, not mission-critical infrastructure.

**Too many knobs** is a UX risk. A powerful GUI can become a cockpit. You will need beginner-safe defaults and an “advanced” area.

**Approval fatigue** is real too. If you require confirmation for too many tiny things, you will click through blindly. The gate should exist, but only at meaningful stages.

**Long-run ambiguity** is another one. If the GUI says “loading model, check back later,” users need to know whether the job is healthy, stuck, retrying, or dead. Curated progress is important.

**Asset sprawl** will happen unless naming and folder rules are strict. Variants, bounce loops, previews, proofs, approved finals, target-specific outputs — this gets messy quickly.

**Aspect-ratio drift** can make section art inconsistent if one section is designed for 16:9 and another for 9:16 first. You need a strategy: per-target generation vs master-safe composition.

**One-off hacks becoming architecture** is a big danger. Birthday-video shortcuts can quietly harden into the permanent pipeline unless you explicitly label them as hacks.

A very good next note for later would be:
“GUI must distinguish candidate, approved, and final artifacts everywhere, and must show safe-zone subtitle previews across all target aspect ratios before render.”

5. WHAT WE LEARNED FROM LOCAL COMFYUI TESTING
======================================================================

5.1 Image side
Local Flux still-image generation is usable.
A bar-vibe still was successfully generated and looked good.

5.2 Image-to-video side
Local Wan i2v is usable only for subtle atmospheric loops.
It is not the backbone for complex realistic video.

5.3 Important observed behavior
- one early Wan run was “good enough”
- one later run collapsed into horrible artifacted nonsense
- a recovery run had less happening, but no catastrophic destruction
- this suggests subtle near-static motion is safer than semantic motion like “dust visibly falling”
- a very subtle zoom / life effect may be more viable than trying to force “real footage” style particle behavior

5.4 Practical conclusion
Use Wan for:
- very subtle ambient motion
- faint particles
- smoke/fog/light flicker
- gentle “alive” feeling

Do not rely on Wan for:
- complex camera motion
- characters
- precise realism
- obvious scene events

5.5 Loopability trick
Bounce loops are a strong option:
- play forward
- then reverse
- avoid duplicated seam frame if practical
- use FFmpeg postprocess for this
Especially useful for ultra-subtle motion clips.
